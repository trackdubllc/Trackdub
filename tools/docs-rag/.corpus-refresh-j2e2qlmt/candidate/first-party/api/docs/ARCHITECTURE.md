# Architecture — Authentication flow & request lifecycle

This document covers the portal API Worker (`src/index.ts`,
`wrangler.jsonc`) only. Desktop license activation is a separate Worker with
its own D1 and secrets — see `docs/ACTIVATION-CONTRACT.md` and
`src/activation/`.

## Topology

```
portal.trackdub.com                    api.trackdub.com (this Worker)
  React SPA, browser only                Hono + Better Auth + D1 + Drizzle
  fetch(..., credentials:"include") ───►  /api/auth/*   (Better Auth)
  no auth logic, no cookie reads          /api/health, /api/version
  route guards are UX only                /api/languages (public)
                                          /api/admin/invite (operator token)
                                          /api/dubs* (session; R2 MEDIA upload)
```

There is **no auth proxy**. The browser calls the Worker directly. The Worker is
the only authorization boundary — the portal's route guards are a UX nicety and
are never trusted.

## Session & cookie model

Sessions are cookie-based and **host-only** to `api.trackdub.com`:

- Cookie attributes: `Secure; HttpOnly; SameSite=Lax; Path=/`, **no `Domain`**.
- Host-only is achieved by (a) **omitting `baseURL`** so Better Auth derives the
  origin from request headers, and (b) leaving `crossSubDomainCookies`
  **disabled**. See `src/auth/index.ts`.
- The cookie is `HttpOnly`, so portal JavaScript can never read the session
  token. The portal only ever observes auth state via `GET /api/auth/session`.

Because the portal and API are on different subdomains, every portal request is
**cross-origin** and sent with `credentials: "include"`. That guarantees the
browser attaches both the session cookie and an `Origin` header — which Better
Auth requires for CSRF protection on state-changing requests (see
CONTRACT-MISMATCHES.md §CSRF).

## Request lifecycle

Every request flows through this chain (`src/index.ts`):

1. **request-id** — mint/propagate `x-request-id` (honors inbound `cf-ray`).
2. **logging** — structured JSON access log emitted after the handler with
   `requestId, method, path, status, durationMs`.
3. **CORS** — origin checked against the allowlist (`PORTAL_ORIGIN` + localhost).
   Credentials enabled; never `*`; `OPTIONS` preflight handled.
4. **routing**
   - `/api/auth/*` → Better Auth handler (plus a `/api/auth/session` alias).
   - `/api/health*`, `/api/version`, `/api/languages` → public, no session required.
   - `/api/admin/*` → `requireAdminToken` (operator bearer token).
   - `/api/dubs*` → `requireAuth` (session cookie). Upload writes R2 `MEDIA`;
     create inserts a Queued `dub_jobs` row. No cloud inference yet.
5. **error handling** — `app.onError` maps `ApiError` → its status/code, config
   errors and anything unexpected → generic 500. Stack traces are logged, never
   returned. All errors share `{ error: { code, message, requestId } }`.

## Authentication flows

### Sign in
`POST /api/auth/sign-in/email { email, password }` → Better Auth verifies the
credential account, creates a session row in D1, and returns the host-only
`Set-Cookie`. The portal stores nothing; the browser holds the cookie.

### Session check
`GET /api/auth/session` (aliased to Better Auth `get-session`) reads the cookie,
validates the session in D1, and returns `{ user, session } | null`. Portal
route guards call this (memoized) purely for UX.

### Sign out
`POST /api/auth/sign-out` invalidates the session row and clears the cookie.

### Forgot / reset password
`POST /api/auth/forget-password { email, redirectTo }` issues a reset token;
`POST /api/auth/reset-password { token, newPassword }` consumes it and (per
config) revokes existing sessions. PR1 has no email provider — the reset link is
logged (non-production only); email delivery is a later PR.

### Invite-only registration
Public sign-up is disabled (`disableSignUp: true`). Users are provisioned by an
operator via `POST /api/admin/invite` (guarded by `ADMIN_API_TOKEN`), which
creates the user + credential account through Better Auth's internal context
(`src/auth/provision.ts`) — mirroring exactly what the sign-up route does, but
bypassing the disabled public endpoint. Real invites then start the reset flow;
the bootstrap/seed path may set an initial password directly.

## Database

D1 (SQLite) accessed through Drizzle. Schema (`src/db/schema.ts`) includes the
Better Auth core set (`user`, `session`, `account`, `verification`) plus
`dub_jobs` for portal cloud jobs. Migrations are generated by Drizzle Kit into
`drizzle/` and applied with `wrangler d1 migrations apply`. D1 has no interactive
transactions; Better Auth's D1 dialect uses `batch()` for atomicity. Billing and
API-key tables are still deferred.

## Testing

Tests run in real `workerd` via `@cloudflare/vitest-pool-workers`, against an
isolated D1 with migrations applied at startup. Coverage: health/readiness,
version, CORS (allow/deny/preflight), error envelope + no-stack-leak, auth
middleware (401), authorization middleware (403), and the full session lifecycle
(sign-in → host-only cookie → protected access → session read → sign-out →
re-protected).
